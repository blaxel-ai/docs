<Note>
  This feature is currently in private preview and is not recommended for production use. It requires a feature flag on your workspace: [contact us](https://blaxel.ai/contact) or email [support@blaxel.ai](mailto:support@blaxel.ai) to get access. Until then, the Agent Proxy secrets page is hidden in the Blaxel console and the `/secrets` API operations answer `403 Forbidden`.
</Note>

Workspace secrets are named credentials stored once per workspace and resolved by the [Blaxel proxy](/Sandboxes/Proxy) when a sandbox request matches a routing rule. Reference them with the same `{{SECRET:name}}` syntax as [rule-level secrets](/Sandboxes/Proxy-secrets-injection), without repeating the value in every sandbox spec.

## How workspace secrets work

- A secret is a name and a value. The value is encrypted at rest and is write-only: no API, CLI, SDK or console view returns it.
- Setting a secret that already exists creates a new version. The proxy always resolves the latest version, so rotating a key takes effect on the next proxied request of every sandbox in the workspace, with no restart.
- Any routing rule in the workspace can reference a workspace secret in its `headers` or `body` values. The rule does not need a `secrets` map for it.
- Resolution order is the routing rule first, then the workspace. A rule-level secret with the same name takes precedence over the workspace secret.
- When a referenced name exists neither on the rule nor in the workspace, the proxy skips that header or body field instead of sending a blank value. A `{{SECRET:name}}` placeholder sent by code inside the sandbox is forwarded as literal text in that case.
- Names are case-sensitive and must match `^[A-Za-z0-9_-]{1,128}$`.
- Workspace admins can set and delete secrets. Every workspace member can list secret names and dates.

## Set a secret

<Tabs>
<Tab title="Console">
  Open your workspace in the Blaxel console, go to Security > Agent Proxy secrets, and click Add secret. Enter a name and a value. To rotate a secret, click Set new value on its row.
</Tab>
<Tab title="CLI">
  Read the value from an environment variable, a file, or stdin so it does not end up in your shell history:

  ```bash
  export STRIPE_KEY="sk_live_..."
  bl secret set stripe-key --from-env STRIPE_KEY

  # or
  cat stripe-key.txt | bl secret set stripe-key
  ```
</Tab>
<Tab title="TypeScript">
  ```typescript
  import { SecretInstance } from "@blaxel/core";

  await SecretInstance.set("stripe-key", process.env.STRIPE_KEY!);
  ```
</Tab>
<Tab title="Python">
  ```python
  import os
  from blaxel.core import SecretInstance

  await SecretInstance.set("stripe-key", os.environ["STRIPE_KEY"])
  ```

  Use `SyncSecretInstance` from `blaxel.core` for synchronous code.
</Tab>
<Tab title="API">
  ```bash
  curl -X POST https://api.blaxel.ai/v0/secrets \
    -H "Authorization: Bearer $BL_API_KEY" \
    -H "X-Blaxel-Workspace: my-workspace" \
    -H "Content-Type: application/json" \
    -d '{"name": "stripe-key", "value": "sk_live_..."}'
  ```
</Tab>
</Tabs>

The response contains the secret name and timestamps only.

## Reference a workspace secret from a routing rule

Create the sandbox with a routing rule that uses `{{SECRET:stripe-key}}` and no `secrets` map:

<CodeGroup>

```typescript TypeScript
import { SandboxInstance } from "@blaxel/core";

const sandbox = await SandboxInstance.create({
  name: "my-sandbox",
  image: "blaxel/base-image:latest",
  region: "us-was-1",
  network: {
    proxy: {
      routing: [
        {
          destinations: ["api.stripe.com"],
          headers: {
            "Authorization": "Bearer {{SECRET:stripe-key}}",
          },
        },
      ],
    },
  },
});
```

```python Python
from blaxel.core.sandbox import SandboxInstance

sandbox = await SandboxInstance.create({
    "name": "my-sandbox",
    "image": "blaxel/base-image:latest",
    "region": "us-was-1",
    "network": {
        "proxy": {
            "routing": [
                {
                    "destinations": ["api.stripe.com"],
                    "headers": {
                        "Authorization": "Bearer {{SECRET:stripe-key}}",
                    },
                },
            ],
        },
    },
})
```

</CodeGroup>

Code inside the sandbox calls `api.stripe.com` normally. The proxy resolves `stripe-key` from the workspace and injects the header. The sandbox never sees the value, and the sandbox spec never contains it.

Code inside the sandbox can also send `{{SECRET:stripe-key}}` in its own request headers or body, as with rule-level secrets.

## List secrets

Listing returns names and dates only.

<Tabs>
<Tab title="CLI">
  ```bash
  bl secret list
  # or
  bl get secrets
  ```
</Tab>
<Tab title="TypeScript">
  ```typescript

  for (const secret of secrets) {
    console.log(secret.name, secret.updatedAt);
  }
  ```
</Tab>
<Tab title="Python">
  ```python
  for secret in await SecretInstance.list():
      print(secret.name, secret.updated_at)
  ```
</Tab>
<Tab title="API">
  ```bash
  curl https://api.blaxel.ai/v0/secrets \
    -H "Authorization: Bearer $BL_API_KEY" \
    -H "X-Blaxel-Workspace: my-workspace"
  ```
</Tab>
</Tabs>

## Rotate a secret

Set the secret again with the new value. The previous version is kept in the backend but is no longer used: the proxy resolves the latest version on the next request of every sandbox that references the name.

```bash
bl secret set stripe-key --from-env NEW_STRIPE_KEY
```

## Delete a secret

Deleting removes the secret and all its versions. Routing rules that still reference the name stop injecting the corresponding header or body field.

<Tabs>
<Tab title="CLI">
  ```bash
  bl secret delete stripe-key
  ```
</Tab>
<Tab title="TypeScript">
  ```typescript
  await SecretInstance.delete("stripe-key");
  ```
</Tab>
<Tab title="Python">
  ```python
  await SecretInstance.delete("stripe-key")
  ```
</Tab>
<Tab title="API">
  ```bash
  curl -X DELETE https://api.blaxel.ai/v0/secrets/stripe-key \
    -H "Authorization: Bearer $BL_API_KEY" \
    -H "X-Blaxel-Workspace: my-workspace"
  ```
</Tab>
</Tabs>

## Availability

Workspace secrets are resolved in every region where the proxy is available on the current sandbox infrastructure; see [region availability](/Sandboxes/Proxy#region-availability). Setting or deleting a secret pushes the change to each of these regions before the request returns. If a region cannot be reached, the request answers `503` and names the region: retry the same request to complete the propagation.
