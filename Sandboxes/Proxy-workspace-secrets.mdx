<Note>
  This feature is currently in private preview and is not recommended for production use. It requires a feature flag on your workspace: [contact us](https://blaxel.ai/contact) or email [support@blaxel.ai](mailto:support@blaxel.ai) to get access. Until then, the Proxy secrets page is hidden in the Blaxel console and the `/secrets` API operations answer `403 Forbidden`.
</Note>

Workspace secrets are named credentials stored once per workspace and resolved by the [Blaxel proxy](/Sandboxes/Proxy) when a sandbox request matches a routing rule. Reference them with the same `{{SECRET:name}}` syntax as [rule-level secrets](/Sandboxes/Proxy-secrets-injection), without repeating the value in every sandbox spec.

Each workspace secret is **scoped to destinations**: the hosts, optionally with a path pattern, it may be sent to. The proxy only substitutes the placeholder when the outbound request goes to one of them.

## How workspace secrets work

- A secret is a name, a value and a list of destinations. The value is encrypted at rest and is write-only: no API, CLI, SDK or console view returns it.
- Setting a secret that already exists creates a new version. The proxy always resolves the latest version, so rotating a key takes effect on the next proxied request of every sandbox in the workspace, with no restart.
- Any routing rule in the workspace can reference a workspace secret in its `headers` or `body` values. The rule does not need a `secrets` map for it.
- Resolution order is the routing rule first, then the workspace. A rule-level secret with the same name takes precedence over the workspace secret.
- A workspace secret is only resolved when the request's host and path match one of its destinations. Toward any other destination it behaves like a name that does not exist.
- When a referenced name cannot be resolved, the proxy skips that header or body field instead of sending a blank value. A `{{SECRET:name}}` placeholder sent by code inside the sandbox is forwarded as literal text in that case.
- Names are case-sensitive and must match `^[A-Za-z0-9_-]{1,128}$`.
- Workspace admins can set and delete secrets. Every workspace member can list secret names, destinations and dates.

## Destinations

Destinations use the same syntax as the `destinations` of a routing rule:

| Destination | Matches |
|---|---|
| `api.stripe.com` | any path on that host |
| `*.example.com` | any subdomain of example.com |
| `api.example.com/v1/*` | paths under `/v1/` on that host |
| `api.example.com/v1/charges` | that exact path |

A secret needs at least one destination and at most 50, each at most 512 characters. `*` alone is rejected: a workspace secret must name the hosts it may reach.

## Set a secret

<Tabs>
<Tab title="Console">
  Open your workspace in the Blaxel console, go to Proxy secrets, and click Add secret. Enter a name, a value and the destinations, one per line or comma-separated. To rotate a secret, click Rotate on its row: the current destinations are pre-filled.
</Tab>
<Tab title="CLI">
  Pass the value on stdin so it does not end up in your shell history. `--destination` (`-d`) is repeatable and accepts comma-separated values:

  ```bash
  echo -n "$STRIPE_KEY" | bl secret set stripe-key -d api.stripe.com

  # several destinations, including a path pattern
  echo -n "$GITHUB_TOKEN" | bl secret set github-token \
    -d api.github.com -d "uploads.github.com/repos/*"

  # or with the value as a flag
  bl secret set stripe-key --value "sk_live_..." --destination api.stripe.com
  ```
</Tab>
<Tab title="TypeScript">
  ```typescript
  import { SecretInstance } from "@blaxel/core";

  await SecretInstance.set("stripe-key", process.env.STRIPE_KEY!, ["api.stripe.com"]);
  ```
</Tab>
<Tab title="Python">
  ```python
  import os
  from blaxel.core import SecretInstance

  await SecretInstance.set("stripe-key", os.environ["STRIPE_KEY"], ["api.stripe.com"])
  ```

  Use `SyncSecretInstance` from `blaxel.core` for synchronous code.
</Tab>
<Tab title="Go">
  ```go
  client := blaxel.NewClient()

  _, err := client.Secrets.New(ctx, blaxel.SecretNewParams{
      Secret: blaxel.SecretParam{
          Name:         "stripe-key",
          Value:        blaxel.String(os.Getenv("STRIPE_KEY")),
          Destinations: []string{"api.stripe.com"},
      },
  })
  ```
</Tab>
<Tab title="API">
  ```bash
  curl -X POST https://api.blaxel.ai/v0/secrets \
    -H "Authorization: Bearer $BL_API_KEY" \
    -H "X-Blaxel-Workspace: my-workspace" \
    -H "Content-Type: application/json" \
    -d '{"name": "stripe-key", "value": "sk_live_...", "destinations": ["api.stripe.com"]}'
  ```
</Tab>
</Tabs>

The response contains the secret name, its destinations and timestamps only. A request without destinations, with `*`, with more than 50 entries or with an entry longer than 512 characters is rejected with `400`.

## Reference a workspace secret from a routing rule

Create the sandbox with a routing rule that uses `{{SECRET:stripe-key}}` and no `secrets` map:

<CodeGroup>

```typescript TypeScript
import { SandboxInstance } from "@blaxel/core";

const sandbox = await SandboxInstance.create({
  name: "my-sandbox",
  image: "blaxel/base-image:latest",
  region: "us-was-1",
  network: {
    proxy: {
      routing: [
        {
          destinations: ["api.stripe.com"],
          headers: {
            "Authorization": "Bearer {{SECRET:stripe-key}}",
          },
        },
      ],
    },
  },
});
```

```python Python
from blaxel.core.sandbox import SandboxInstance

sandbox = await SandboxInstance.create({
    "name": "my-sandbox",
    "image": "blaxel/base-image:latest",
    "region": "us-was-1",
    "network": {
        "proxy": {
            "routing": [
                {
                    "destinations": ["api.stripe.com"],
                    "headers": {
                        "Authorization": "Bearer {{SECRET:stripe-key}}",
                    },
                },
            ],
        },
    },
})
```

</CodeGroup>

Code inside the sandbox calls `api.stripe.com` normally. The proxy resolves `stripe-key` from the workspace and injects the header. The sandbox never sees the value, and the sandbox spec never contains it.

The rule's `destinations` decide which requests go through the rule; the secret's destinations decide where its value may be injected. Code inside the sandbox can also send `{{SECRET:stripe-key}}` in its own request headers or body, as with rule-level secrets, under the same destination check.

<Warning>
  If a rule sends `{{SECRET:stripe-key}}` toward a host that is not among the secret's destinations, the header or body field is skipped. Scope the secret to every host that legitimately needs it.
</Warning>

## Rotate a secret

Set the secret again with the new value and its destinations; the destinations you pass replace the previous ones. The previous version is kept in the backend but is no longer used: the proxy resolves the latest version on the next request of every sandbox that references the name.

```bash
echo -n "$NEW_STRIPE_KEY" | bl secret set stripe-key -d api.stripe.com
```

## Delete a secret

Deleting removes the secret and all its versions. Routing rules that still reference the name stop injecting the corresponding header or body field. Deleting a name that no longer exists succeeds.

<Tabs>
<Tab title="CLI">

  ```bash
  bl secret delete stripe-key
  ```

## Availability

Workspace secrets are resolved in every region where the proxy is available on the current sandbox infrastructure; see [region availability](/Sandboxes/Proxy#region-availability). Setting or deleting a secret returns as soon as the change is stored; it is then replicated to each region, normally within seconds. A region that cannot be reached is retried for up to two hours and converges on its own once it is back, so there is no need to retry the write.
