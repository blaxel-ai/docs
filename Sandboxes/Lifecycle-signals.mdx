title: 'Lifecycle signals'
description: 'Let sandbox code clean up before deletion and prepare before standby with SIGTERM and SIGUSR2 grace periods.'
---

You can have your sandbox warned before it is deleted or put on standby. Blaxel sends a signal to the processes running in your sandbox, then gives them a grace period to act before it continues.

| Event | Signal | Setting | Maximum |
| --- | --- | --- | --- |
| Deletion | `SIGTERM` | `terminationGracePeriodSeconds` | 30 seconds |
| Standby | `SIGUSR2` | `standbyGracePeriodSeconds` | 10 seconds |

Both settings default to `0`: no signal is sent and the sandbox is deleted or put on standby right away. A value above the maximum or below `0` is rejected with a `400` error.

## Configure the grace periods

Set the grace periods in the `[runtime]` section of the `blaxel.toml` of your [sandbox template](./Templates), then deploy it with `bl deploy`:

```toml
[runtime]
terminationGracePeriodSeconds = 30
standbyGracePeriodSeconds = 10
```

The same fields are available in `spec.runtime` when you create a sandbox through the API. They are read when the sandbox is created, so changing them requires a new sandbox.

## Handle deletion

When a sandbox with a termination grace period is deleted, its processes receive `SIGTERM`. The sandbox is deleted as soon as they exit, or when the grace period ends, whichever comes first. A sandbox in standby is resumed first so that it can receive the signal, and the time to resume counts against the grace period.

<CodeGroup>

```typescript TypeScript
process.on("SIGTERM", async () => {
  await flushPendingWork();
  process.exit(0);
});
```

```python Python
import signal
import sys

def on_sigterm(signum, frame):
    flush_pending_work()
    sys.exit(0)

signal.signal(signal.SIGTERM, on_sigterm)
```

</CodeGroup>

## Handle standby

When a sandbox with a standby grace period goes idle, its processes receive `SIGUSR2`. The sandbox keeps running across the standby: use the signal to flush buffers, write a checkpoint or close outbound connections.

By default, Blaxel waits for the full grace period before the standby. To go on standby as soon as your code is ready, use the keep-alive counter exposed in the `BLAXEL_SCALE_FILE` environment variable:

- Write `+1` to the file when your code starts preparing
- Write `-1` when it is done, even if the preparation fails: the sandbox goes on standby right away

If the counter is still above `0` when the grace period ends, the standby is cancelled and the sandbox keeps running. Any activity on the sandbox during the grace period also cancels the standby.

<CodeGroup>

```typescript TypeScript
import { writeFileSync } from "node:fs";

process.on("SIGUSR2", async () => {
  writeFileSync(process.env.BLAXEL_SCALE_FILE!, "+1");
  try {
    await saveCheckpoint();
  } finally {
    writeFileSync(process.env.BLAXEL_SCALE_FILE!, "-1");
  }
});
```

```python Python
import os
import signal

def on_sigusr2(signum, frame):
    scale_file = os.environ["BLAXEL_SCALE_FILE"]
    with open(scale_file, "w") as f:
        f.write("+1")
    try:
        save_checkpoint()
    finally:
        with open(scale_file, "w") as f:
            f.write("-1")

signal.signal(signal.SIGUSR2, on_sigusr2)
```

</CodeGroup>

<Warning>
  The default action of `SIGUSR2` is to terminate the process. Blaxel only sends it to processes that install a handler for it, so processes without one are not affected.
</Warning>

## Which processes receive the signals

The [sandbox API](./Templates#2-customize-the-dockerfile) receives both signals and passes them on to the processes it started: the `--command` of the image and the processes started through the [process API](./Processes). On deletion, it waits for all of them to exit before it shuts down.

If the entrypoint of your image is your own program rather than the sandbox API, it receives both signals directly.
