By default, everything inside a sandbox runs as `root`. You can instead declare an unprivileged user in your image, so processes, terminals and filesystem operations run as that user while the sandbox API keeps the privileges it needs for drive mounts, networking and keep-alive.

<Note>
  Non-root user isolation is available on [Carbon (Mark 3.1)](/Infrastructure/Gens#carbon-aka-mark-31). Carbon is enabled by default for new workspaces in the `us-pdx-1` and `us-was-1` regions, and is rolling out progressively to existing workspaces. On the previous generation, create the sandbox with the [`iptables: enabled`](/Sandboxes/Overview#kernel-networking) extra arg.
</Note>

## Why the sandbox API stays root

The sandbox API is PID 1 in the sandbox. It mounts [Agent Drive](/Agent-drive/Overview), configures egress networking, installs the CA bundle and manages standby, and all of those require root.

This is why a plain `USER` directive is not enough on its own: in a plain container it de-privileges the sandbox API itself, which breaks everything mentioned above. On Blaxel, the runtime does not apply the image `USER` to the sandbox API. It starts the API as root and passes your user down to it, and the API drops privileges for the operations it runs on your behalf, keeping root only for the infrastructure work listed below.

<Warning>
  Running the same image locally with `docker run` applies `USER` to the entrypoint, so drive mounts and networking setup fail, and root-only preparation in an entrypoint script fails too. Skip the preparation in the script when it does not run as root (`[ "$(id -u)" = 0 ]`).
</Warning>

<Note>
  This scopes privileges inside the sandbox. It is a defense-in-depth measure: the microVM boundary remains the isolation guarantee between your sandbox and everything else.
</Note>

## Declare a user in your image

Create the user in your Dockerfile, declare it with `USER`, and turn the feature on with `BL_SANDBOX_USER_ENABLED`:

```docker
FROM node:24-alpine

RUN adduser -D -u 10001 -h /blaxel app
WORKDIR /blaxel

COPY --from=ghcr.io/blaxel-ai/sandbox:latest /sandbox-api /usr/local/bin/sandbox-api

USER app

ENV HOME=/blaxel
ENV BL_SANDBOX_USER_ENABLED=true

ENTRYPOINT ["/usr/local/bin/sandbox-api"]
```

The user follows Docker `USER` syntax: `app`, `10001`, `app:app` or `10001:10001`. The user must exist in the image, and it cannot resolve to uid 0. Make sure your workload owns every directory it writes to.

### Prepare the sandbox as root at boot

If you need root-only preparation at boot, such as a `chown`, a `mkdir` outside the user's home or firewall rules, use an entrypoint script that hands over to the sandbox API with the `--user` flag:

```bash
#!/bin/sh
set -eu

chown -R app /blaxel

exec /usr/local/bin/sandbox-api --user app "$@"
```

Keep `USER app` in the Dockerfile and point `ENTRYPOINT` at the script. On Blaxel, the entrypoint of a sandbox always starts as root, whatever the image `USER`. The `USER` directive also keeps the ownership you set in the Dockerfile: in an image without `USER`, every file is owned by root. The `--user` flag is the explicit opt-in, so it does not need `BL_SANDBOX_USER_ENABLED`. Setting `BL_SANDBOX_USER` in your image environment is equivalent to `USER`, and still requires the enable variable.

A background process the script starts before the `exec` keeps running as root. To start one as your user, use the standard tools, such as `su-exec app <command> &` or `setpriv --reuid=app --regid=app --init-groups <command> &`.

Firewall rules (`nft`, `iptables`) added by the script stay in place for the life of the sandbox, including across standby and an out-of-memory kill. Write them so the script can run them again, because it runs on every boot.

## What runs as your user vs. stays root

| Runs as your user | Stays root |
|---|---|
| Processes, startup and background commands | Agent Drive mounts |
| Terminal sessions | Egress and networking setup |
| Code execution | CA bundle installation |
| Filesystem API calls (read, write, upload, search) | Keep-alive and standby control |

Calls to the sandbox API from inside a sandbox process keep the same identity. There is no parameter or environment variable that asks for root, so a process cannot use the API to escalate its own privileges. To refuse those calls altogether, [isolate the sandbox API](#isolate-the-sandbox-api).

## Isolate the sandbox API

Calls to the sandbox API through Blaxel require credentials. Calls from inside the sandbox to `localhost:8080` do not. Set `BL_SANDBOX_API_ISOLATION` to refuse connections from your workload to the sandbox API, so code running in the sandbox cannot use it to run commands, read files or open terminals:

```docker
USER app

ENV HOME=/blaxel
ENV BL_SANDBOX_API_ISOLATION=true
```

`BL_SANDBOX_API_ISOLATION` also runs your workload as the image `USER`, without `BL_SANDBOX_USER_ENABLED`.

At boot, before your workload starts, the sandbox API installs firewall rules on its port. Refused connections get a TCP reset. The sandbox does not start when the rules cannot be installed.

| Caller | Result |
|---|---|
| Authenticated calls through Blaxel (SDK, CLI, console, API) | Allowed |
| Root processes inside the sandbox | Allowed |
| Non-root processes inside the sandbox, on `localhost`, `127.0.0.1`, `::1` or any address of the sandbox | Refused |
| Containers, tunnels or bridges running inside the sandbox | Refused |

Only the sandbox API port is filtered. [Preview URLs](/Sandboxes/Preview-url) and your application ports are not affected.

To check it, open a terminal in the sandbox and run the following commands. The image needs `curl`.

```bash
id -un
curl localhost:8080/health
```

`id -un` prints your image user, and `curl` fails with `Connection refused`. The same call through Blaxel with your credentials still succeeds.

Without a `USER` directive, or with `USER root`, the sandbox API installs the rules, logs a warning and runs your workload as root.

<Warning>
  A workload running as root can bypass API isolation. Root callers are allowed by the rules, and root can remove them or stop the sandbox API. API isolation only protects the sandbox API from workloads running as a non-root `USER`.
</Warning>

## Agent Drive

[Agent Drive](/Agent-drive/Overview) mounts are mapped to your user by default: files on the drive appear owned by your user and are writable by it, without a `chown`.

## Cap the sandbox lifetime

Keep-alive processes keep the sandbox running, and a `ttl-idle` expiration policy only counts while the sandbox is in standby. To set a hard limit that holds whatever runs inside, use a `ttl-max-age` expiration policy, counted from the sandbox creation:

```typescript
lifecycle: {
  expirationPolicies: [{ type: "ttl-max-age", value: "2h", action: "delete" }],
}
```

## Limitations

- Access granted only through a supplementary group of your user is not honored on filesystem API calls, which apply the primary group.
- Files that already exist in the image and belong to root stay read-only for your workload. Change their ownership at build time, in an image that declares `USER`, or in a root entrypoint.
- With neither `BL_SANDBOX_USER_ENABLED` nor `BL_SANDBOX_API_ISOLATION` set, the sandbox runs everything as root.
